上午改的需求，
下午谁的 AI 知道？

ContextMesh 为团队里的 AI 助手提供一份可追溯的项目记忆。产品经理上午确认的变更，可以成为工程师下午写代码、测试同事明天写用例时的依据，即使三个人使用不同的工具。

01　/　怎么做

让一条决定从产品经理的会话，走到工程师的任务里

团队先建一个项目池，为成员分配访问权限。每个人把自己常用的 AI 客户端接到同一项目，各自照常工作。以企业试点的登录方式变更为例。

09:20　产品经理

确认哪一句可以共享

她和助手讨论完试用反馈。助手拟好上方那张决策卡，她补上“仅企业试点”，确认发布。私人讨论和未定方案留在原会话。

09:21　项目池

记下什么变了，哪里仍有效

项目池保存新结论、负责人、来源和生效范围。此后查询企业试点会得到 D-02；查询公众注册仍能得到原来的短信方案。

14:10　工程师

在写代码前拿到依据

他只说“帮我写登录验收用例”。助手按项目工作规则先检索相关决定，区分两类用户，生成用例并附出处。工程师可以点回评审记录核对。

同一句请求，会生成怎样的验收用例？
企业试点验证邮箱登录，公众注册继续验证短信登录。示例依据 · D-02 只替代企业试点条款。两条路径都要覆盖。

最有用的字段是“适用于谁”

“改用邮箱登录”只有半句话。补上“仅限企业试点”，系统才能同时保留公众注册的短信规则。发布者只需确认结论和适用范围，后续哪些设计稿、接口和测试受影响，可以在具体任务开始时再判断。

产品设计

六个值得加入的创新功能

一条决定穿过团队，要经历几个不同的问题：谁有权看，哪个版本生效，哪些工作还沿用旧结论，以及下一位接手的人该从哪继续。下面六项能力围绕同一条登录需求设计。

Context Git · 首版

保留决定的版本和适用范围

负责人确认 D-02 时，记录它替代 D-01 的具体范围、生效时间和原因。查询周三的企业试点返回邮箱规则，查询公众注册仍返回短信规则。按历史日期查询，可以还原当时作决定的依据。

交付给用户

答案里有结论、出处，以及“哪一部分改了”。

Context Firewall · 首版

让项目结论与私人讨论分开

作者预览将要共享的摘要，选择项目和可见成员。服务端在搜索、订阅和交接导出时逐次校验接收者权限。原会话中提到的客户联系方式留在个人侧；有权看摘要的人仍需原系统授权才能打开评审原文。

交付给用户

发布前可见“谁将看到哪段内容”，撤回后新的检索和交接排除该条目。

Context Diff · 第二阶段

发现仍在使用旧决定的工作

测试计划声明企业试点采用短信登录，依据为 D-01。系统将计划与同主题、同适用范围且同时有效的规则比较，标出“短信 → 邮箱”。公众短信测试因范围不同而保留。若两位负责人给出冲突结论，列出双方依据，交给负责人裁定。

交付给用户

一条可核对的差异，附受影响的用例和两端出处。

Context Router · 第二阶段

把变更送到正在做相关任务的人

D-02 发布触发变更事件。服务按项目、登录模块和企业试点标签匹配任务订阅，核对权限后推送给负责试点登录页和验收的成员。同一任务按决定版本去重，未在线的客户端可在下次启动时拉取。

交付给用户

打开验收任务时看到“它引用的登录规则已更新”，并可跳转到差异。

Context Handoff · 第二阶段

交接时保留工作做到哪一步

工程师换班时，从任务引用的决定、已验证的结果和待办生成快照。接手人打开时重新检查权限与版本，有变化就附上交接后的更新。已通过的公众短信测试保留，尚未验证的邮箱过期重试单独列出。

交付给用户

一份可直接开始工作的清单，带上次验证结果、未决问题和下一步。

Multi-Model Intelligence · 后续扩展

让不同模型接力完成同一项工作

研发助手领取接口实现，测试助手领取验收任务，各自读取授权的 D-02。结果登记输入版本、产物引用和状态。提交时如果依据已经变化，结果进入复核，再由任务负责人决定重跑哪些步骤。

交付给用户

从同一条决定追溯到实现和验收，团队可独立更换其中一个模型。

02　/　价值

一条消息发过了，为什么还会返工？

工程师动手时，往往并不知道自己漏读过一条消息。这个功能把查证放在生成方案的那一刻。即使产品经理在开会，工程师也能知道哪部分改了、谁确认的、为什么改。

对发布决定的人

一次确认可以被设计、开发和测试分别引用。代价是发布时要检查摘要和范围；重复解释越频繁，这笔投入越划算。

对执行任务的人

设计师改企业登录页，测试保留公众短信回归用例。每个人得到与手头工作有关的细节，遇到矛盾可以直接找到负责人。

对团队负责人

新人或轮岗成员能循着来源理解一次变更。试点优先选择跨角色交接频繁、成员使用不同 AI 工具的项目。

哪些团队最先受益？

工单上写着“按评审结论调整”，但结论留在产品经理的会话里。开发和测试各自问一遍，各自再向助手解释一遍。这类交接越频繁，团队上下文池的复用价值越高。对于需求稳定、助手能准确读取共享文档的项目，现有文档方案已经足够经济。

开源给团队带来什么？

工作记录保存在团队自己的环境里。客户端适配器可以单独维护，采用新模型时沿用已有的决定和权限规则。开源仓库可收集脱敏的回归用例，例如“企业规则被错误用于公众注册”，帮助团队在升级或切换助手前检验同一套行为。

ContextMesh 的核心差异 · 产品设计目标

需求只改了一半，准确找出该跟着改的那部分工作。

设想 D-01 被两组测试引用。D-02 只调整企业试点。首版要让不同客户端对同一输入给出一致依据：企业走邮箱，公众保留短信。后续让任务和产物保存自己引用的决定版本；新版本生效时，沿引用关系筛出范围重叠的测试，向有权限的负责人发送差异。修订产物登记 D-02 后，该项才算完成复核。

潜在的长期优势来自团队持续积累的三类记录：哪条规则适用于谁、哪些工作依赖它、修改后如何验收。它们能让下一次变更直接列出待复核的工作。团队需要为此维护引用关系，这笔成本应一并计入试点。

用同一张工单比较，差异才算成立

给各方案相同的两份决策、企业与公众两组用例，以及同样的权限。首轮比较不同助手首次选对规则并引出处的比例，同时记录配置和人工维护时间。待差异检测与路由上线，再加入一份过时测试，统计漏提醒、误提醒和完成复核的耗时。只有这些结果优于团队已有方案，才有采用独立上下文层的理由。

03　/　实现可行性

两个人、两个客户端，就能验证第一版

首版拟采用可自托管的开源服务。团队在自己的环境里保存工作记录，仓库发布服务代码和客户端配置。首版先接 Codex 和 Claude Code，从两人的独立会话跑通上面的例子。

一条查询怎样选出正确版本

首版拟用 MCP 工具连接客户端，用 PostgreSQL 保存决策及其版本。客户端负责从当前会话拟出摘要。MCP 只提供调用工具的通道，自动提炼和自动查询需要各客户端自己的工作规则或钩子支持。

决策记录示例

  "id": "D-02", "project": "login",
  "topic": "login.verification",
  "scope": {"segment": "enterprise_pilot"},
  "value": "email_otp", "status": "confirmed",
  "effective_from": "2026-11-25",
  "supersedes": "D-01", "source_ref": "review/42"
}

作者和确认者由服务端从登录身份记录。替代关系只在新记录声明的范围及生效期内有效。

  1. 写入。 publish_decision 校验发布权限和预期版本。在同一事务中保存记录、替代关系和变更事件。客户端重试沿用请求 ID；两人同时改同一版本时，后提交者收到冲突提示。
  2. 查询。 resolve_context 接收主题、业务范围和查询时间。先筛除无权访问、未确认、未生效或已撤回的记录，再应用局部替代关系。文本检索用于发现候选，最终依据来自有版本的记录。
  3. 处理歧义。 如果任务只说“登录测试”，返回按人群拆分的两条规则；需要单一结论时追问目标用户。若同一范围仍有两个互斥决定，返回待裁定状态和双方来源。时间较新本身不足以推翻已确认的决定。
可快速验证

一位熟悉后端的开发者可先用约 2～5 天跑通两台设备上的显式读写。试点版预估共 2～4 周，包含成员权限、版本替代、安装说明和真实客户端联调。时间为工程估算。

最容易失败

客户端可能忘记检索，也可能把讨论稿当成决定。接入时分别测“能否读写”和“普通任务会不会触发读取”；发布时请负责人确认。冲突未解决时，同时展示来源并标记待定。

试点验收底线

撤回后，新检索应排除该记录；没有项目权限的成员应查不到记录和摘要。已经进入历史会话的副本有独立生命周期，需要明确告知成员。

从团队记忆扩到不同模型协作

试点出现稳定复用后，再适配 WorkBuddy 的工具调用与触发方式，加入按任务订阅变更。等团队出现明确的任务委派需求，再让不同模型驱动的 Agent 通过同一份授权上下文领取任务、提交结果，由负责人验收。

四周试点如何验收

第一周 · 建立基线

用一张发生过返工的脱敏工单还原交接，标注正确答案和所需依据。用现有共享文档与助手重做该任务，记录查证时间和遗漏项。

第二周 · 验证接口

在两台机器上接入两种客户端，分别测试新决定、局部替代、撤回和项目隔离；再测普通工作请求能否触发检索。记录需要人工提醒的次数。

第三周 · 观察使用

在一次真实迭代中记录首次输出、负责人判定、检索复核时间和发布修正时间。漏检索也计入样本，避免只统计成功调用。

第四周 · 判断收益

建议观察至少 10 次交接，其中至少 8 次首次正确使用当前决定，且实际节省的时间高于维护时间。与文档基线比较，并查看成员有无主动复用。上述门槛用于小范围试点，属于设计目标。
